# T302g 4096 Timing Diagnostics

## Purpose

Locate why the new `teacher_elevation_trajectory_mpc_semantic` 4096-env training rollout misses the `10s` collect-data target.

## Stage

Independent MPC semantic RL training config / RSL-RL collect-data timing.

## Related Todo

[T302g](../todo/T302g-mpc-semantic-rl-training-config.md), especially `T302g.5`.

## Command

```bash
/mnt/mydisk/lhy/anaconda3/envs/env_isaacsim/bin/python Go2Pvcnn/scripts/train.py \
  --headless \
  --device cuda:1 \
  --num_envs 4096 \
  --max_iterations 1 \
  --experiment teacher_elevation_trajectory_mpc_semantic \
  --planner-backend mpc
```

## Input Conditions

- Device: `cuda:1`
- Envs: `4096`
- RSL-RL mem guard: `num_steps_per_env 40 -> 24`, `num_mini_batches 4 -> 8`
- MPC quality preserved: `mpc_optimize_steps` not reduced; strict T302 planner losses not changed.
- Timing probe enabled in `Go2Pvcnn/scripts/train.py` for the T302g experiment.

## Key Metrics

- OOM fixed: the command reaches training and writes `model_0.pt`.
- TensorBoard `Perf/collection_time` samples:
  - `86.56s` after initial OOM fixes with scanner chunk `64`
  - `76.67s` with scanner chunk `512`
  - `83.10s` with lower semantic scanner update period experiment
  - `75.88s` with reward-term timing
  - `82.66s` with MPC runtime counters enabled
- Step timing with CUDA sync:
  - `sim.step`: about `98-122ms` after warmup
  - `observation.compute`: about `9-10ms` after warmup
  - `swing_leg_collision`: about `3.5-5.7ms`
  - `reference_foot_pos`: about `2.65-2.90s` after warmup; first step about `5.12s`
  - MPC counters show `selected_dirty_count=64`, `dirty_backlog` decreasing by `64` per step, `planner_ms` about `2.65-2.86s`, `cache_ms < 1ms` after first step.

## Result

Partial pass. The user command is valid and no longer fails at scene replication, inference-mode tensors, semantic scanner OOM, or reward scanner OOM. The 4096 rollout still misses the `10s` target.

## Conclusion

The current bottleneck is the MPC optimizer invoked through `reference_foot_pos_reward`, not the new swing collision reward or semantic observation. The dirty-subset scheduler replans `64` env rows per step, and each `64`-row MPC `plan_segment` takes about `2.7s` with current T302 quality settings. With a first-cache backlog of `4096`, the first 24-step rollout spends most collect time draining the planner backlog.

## Follow-Up

- Add a T302g child for MPC planning throughput optimization without lowering T302 strict metrics.
- Candidate directions:
  - reduce first-rollout backlog pressure via cheaper initial fallback plus lower-priority planning warmup
  - optimize `plan_segment` for `64`-row batches
  - tune `mpc_max_dirty_envs_per_step` only after measuring planner time per batch and resulting backlog
  - consider a cached/static reference bootstrap for early RL collection, while preserving selected-row current-state replans for dirty envs
